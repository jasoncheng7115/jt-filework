# ADR-0004: SFTP support

- **Status:** Accepted — the project owner chose Option A and asked for
  QSpace's shape: saved connections that open in a pane and browse like any
  other folder. Being built in the two stages below.
- **Date:** 2026-08-30
- **Deciders:** project owner

## Context

The project owner has asked for SFTP. `docs/PRODUCT_SPEC.md` §13 already
anticipates "future remote API providers", and the seam for it exists:
`jtf_fs::Provider` is a trait with `handles`, `list` and `enumerate_async`,
and `LocalProvider` is one implementation of it. A remote filesystem is
another.

Three things are *not* in place, and each is a decision rather than a
detail.

### 1. `Location` has no remote variant

`Location` is `Local { path }`, `ArchiveMember { .. }` and `Virtual { .. }`.
SFTP needs a fourth: a host, a port, a user, and a path on that host.

`Location` is serialized into the session file, so adding a variant is a
session format change: `SESSION_FORMAT_VERSION` goes to 3, a migration step
is added, and a `v3.json` fixture is committed. That is routine here — the
v1→v2 step already exists — but it is not free, and it is the reason this is
not something to add speculatively.

### 2. Credentials

This is the part that decides the shape of everything else.

- **Passwords must not be written by this program.** If a password is needed
  it is asked for and kept in memory for as long as the process runs, so that
  reconnecting does not ask again; it is dropped when the user disconnects,
  and it never reaches the disk. Anything else means jt-filework owns a
  credential store, and a file manager should not.

  **Amended after the first build.** This originally said "asked for, used,
  and forgotten", and the implementation forgot it after one successful
  connection. That made a password-only server usable exactly once: a dropped
  connection, an explicit disconnect, or the next launch restoring a remote
  tab all reached the connect path with nothing to sign in with, the server
  refused, and the pane reported "you do not have permission" for a folder the
  account could read perfectly well. Re-typing a password per reconnect is not
  a security property, only an obstacle - what the property is actually about
  is the disk, and that has not changed.
- **Keys are the expected path.** `~/.ssh/id_*`, an agent via `SSH_AUTH_SOCK`,
  and `~/.ssh/config` for host aliases, ports and identity files. A user who
  can `sftp host` in a terminal should be able to type the same host here.
- **Host keys must be verified against `~/.ssh/known_hosts`.** A mismatch is
  refused and reported, never "continue anyway" behind a checkbox. An unknown
  host is a question asked once, and the answer is written to `known_hosts` —
  the same file the rest of the system uses, not a private one.

### 3. Everything above the provider assumes local paths

`Plan::build` measures a copy by walking the filesystem. `folder_size` walks
it. The viewer opens a `File`. Trash goes through the platform. None of these
work against a remote host, and each needs either a remote implementation or
an honest refusal:

| Feature | Remote answer |
|---|---|
| List, navigate, sort, filter | The provider does it |
| Copy / move **to and from** local | Streamed by the job engine; this is the point of the feature |
| Copy / move **within** the remote | A server-side rename where possible, else download-and-upload |
| Rename, mkdir, delete | Direct SFTP operations |
| Trash | Refused: SFTP has no trash. Delete is permanent and must say so |
| Folder size | Works, but is slow enough that it must stay on-demand |
| Viewer / preview | Streamed like a local file; the line index already streams |
| Quick Look, Reveal, Open With, terminal | Refused — they are about local files |
| Search | Works, but every directory is a round trip; the existing cancellation matters more here than anywhere |

## Options

### A. `russh` + `russh-sftp` (Rust protocol stack)

- The protocol, the key handling and the SFTP layer are Rust, so nothing
  written in C parses what a server sends — which is where SSH
  implementations have historically gone wrong.

  **Corrected after the fact.** This first said "pure Rust" and "no C
  dependency", and that is not true: russh's default crypto backend is
  `aws-lc-rs`, whose `aws-lc-sys` is C and assembly, and it is why a Windows
  build needs NASM. The alternative backend, `ring`, is also C and assembly,
  so there was no pure-Rust option to choose and the comparison below was
  decided on a property option A did not have. The decision stands — a Rust
  protocol stack over a C one is still the right trade — but it should have
  been argued on what it actually is.
- Actively maintained, async, and the SFTP crate is a separate small layer.
- Uses `ssh-key` for key files; agent support and `~/.ssh/config` parsing are
  ours to write.
- The largest dependency tree of the three.

### B. `ssh2` (libssh2 bindings)

- Mature, and the API is small and synchronous — which suits
  `enumerate_async`, since that already runs on its own thread.
- Brings C code and a build-time dependency on libssh2 and OpenSSL. That is a
  real cost on Windows in particular, and it puts C in the process.

### C. Mount it and stay local

Tell the user to mount the host (`sshfs`, macOS Finder's "Connect to Server",
Windows' SFTP drives) and use the existing local provider.

- No new code, no new dependency, and every feature above works because the
  paths are local.
- But it is not the feature that was asked for, it depends on software this
  program does not ship, and on macOS it needs a kernel extension that recent
  releases discourage.

## Recommendation

**Option A**, in two stages, with these conditions:

1. **Stage one — read only.** `Location::Remote`, a `SftpProvider`, listing,
   navigation, sorting, filtering, the viewer, and copying *from* remote to
   local. No writes to the server at all. This is most of the value and none
   of the risk of a half-finished write path.
2. **Stage two — writes.** Upload, rename, mkdir, delete, and copy within the
   remote.
3. Keys and agent only to begin with. A password prompt comes later if it is
   wanted, and even then the password is never written to disk.
4. Host keys verified against `~/.ssh/known_hosts`. A changed host key is a
   refusal with the fingerprints shown, not a warning that can be clicked
   past.
5. Every operation that cannot work remotely refuses in the UI rather than
   failing when run — the same rule the close control follows: a control that
   is present and does nothing reads as a fault.
6. The connection lives on its own thread, as enumeration already does. A
   hung server must never reach the UI thread.
7. `SESSION_FORMAT_VERSION` goes to 3 with a migration and a fixture. A
   session holding a remote tab must reopen without the host being reachable —
   it shows as disconnected, not as an error at startup.

## Consequences

This is the largest single addition since the workspace model, and the first
that puts the network in the data path. The `Provider` seam means the file
list, sorting, filtering and search do not change; almost all of the work is
the provider, the credential handling and the honest refusals.

The alternative worth weighing is Option C: it is free today and it works.
The case against it is that it is not this program doing the job.

Until this is decided, SFTP is not built, and `Location` keeps three variants.
