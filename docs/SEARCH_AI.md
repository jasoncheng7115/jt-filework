# jt-filework — Search and AI Specification

The governing rule is `AGENTS.md` §15: **deterministic search is first-class
and AI never silently replaces it.**

---

## 1. Two Systems, One Result Model

```text
deterministic query ─┐
                     ├─> ResultSet (virtual folder) ─> Pane/Tab
natural language ────┘
```

A `ResultSet` behaves as a virtual folder: same selection, marking, columns,
sorting and operations as a real directory, plus a Path column and the
provenance of each row.

```text
ResultRow {
  entry: FileEntry,
  provenance: Deterministic | Semantic | Reranked,
  score: Option<f32>,
  explanation: Option<LocalizedText>,
}
```

Provenance is always present and always visible in the UI. The user can always
tell why a row is there.

## 2. Deterministic Search

### 2.1 Query surface

- filename: literal, glob/wildcard, regex
- path and extension
- kind / MIME / platform content type
- size ranges
- timestamps: modified, created, accessed — absolute and relative
- attributes and permissions
- tags (macOS Finder tags, xattr-backed elsewhere)
- metadata fields
- content: literal and regex, with encoding handling
- boolean composition: AND, OR, NOT, grouping

### 2.2 Query syntax

A typed, parseable syntax with a stable grammar:

```text
name:*.log size:>100MB modified:<7d NOT path:*/cache/*
content:/error\s+\d{3}/ kind:archive
```

Rules:
- the parser is fuzzed (`TESTING.md` §9.1)
- a parse error is precise: position, expected token, localized message plus a
  machine-readable code
- an unknown field is an error, never a silently ignored term

### 2.3 Execution

```text
query -> parser -> plan -> {index lookup | live scan} -> filter -> results
```

- live scan is always available and always correct; no index is required
- an index, where present, is an accelerator whose results must match the live
  scan for the same query (a test asserts this)
- scopes: this tab, this pane, workspace, chosen root, or a specific volume
- runs as a Job: incremental results, progress, cancellation
- results stream into the list; the user can act on early results while the
  scan continues

### 2.4 Index (optional)

- opt-in, per root, with a visible size and a visible last-updated time
- stored in SQLite alongside other cached state (`ARCHITECTURE.md` §16)
- the filesystem remains canonical truth; the index is disposable and
  rebuildable
- staleness is detected and reported rather than silently served
- platform accelerators (Spotlight, Windows Search) are optional adapters that
  must be verifiable against the deterministic scanner

### 2.5 Saved searches

Persist as query + scope, reopen as a tab, refresh on demand.

## 3. AI Search

### 3.1 Pipeline

```text
natural language
 -> deterministic filter extraction
 -> exact retrieval (deterministic, authoritative)
 -> optional semantic retrieval
 -> rerank
 -> explanation
```

### 3.2 Non-negotiable guarantees

- Any deterministic component the user expressed — exact name, glob, regex,
  size, date, metadata, explicit filter — is extracted and applied **exactly**.
  AI may not relax, reorder or drop it.
- If the AI layer is unavailable, slow, or returns nonsense, the deterministic
  result set is returned unchanged, with a visible notice.
- Semantic results are **additive** and labelled. They are never merged
  invisibly into deterministic results.
- The AI entry point is a separate, clearly labelled field
  (`UI_UX_SPEC.md` §11). Typing a deterministic query into the deterministic
  field never routes through AI.
- Every AI call is a Job: async, cancellable, progress-reporting.

These are enforced by tests (`TESTING.md` §12).

### 3.3 Semantic index

Optional, opt-in, local-first, per root:
- embeddings generated by a local model where practical
- the index stores derived vectors and file identity, not file contents beyond
  what is required
- an explicit size ceiling and a visible rebuild/delete control
- content never leaves the machine to build the index unless the user has
  explicitly enabled a remote provider

## 4. AI Capabilities Beyond Search

From `PRODUCT_SPEC.md` §13:

- summarize selected files
- compare files
- explain logs, configuration and source
- directory Q&A
- classify and organize
- batch operation planning

Rules for all of them:
- the scope sent to the provider is explicit and shown before the call
- output is presented as an assistant panel, never as authoritative file
  metadata
- **no AI output mutates the filesystem directly.** Anything that would change
  files is produced as a *plan*.

### 4.1 Operation plans

```text
Plan {
  steps: [Operation],
  affected: [FileEntry],
  reversible: bool,
  estimated_cost: …,
}
```

- the plan is rendered as a reviewable list with per-step opt-out
- executing a plan creates ordinary Jobs with ordinary progress, conflict
  resolution, logging and undo-where-safe
- a plan is never executed on generation; a test asserts no mutation occurs
  (`TESTING.md` §12)

## 5. Provider Model

```text
AIProvider
├── ClaudeCodeCLIProvider
├── CodexCLIProvider
├── LocalModelProvider
└── RemoteAPIProvider
```

Every provider declares: capabilities, whether data leaves the machine,
streaming support, cancellation support, and cost characteristics.

### 5.1 External CLI agents (`AGENTS.md` §16, `SECURITY.md` §7)

- spawn with an **argument vector**; never build a shell command line
- explicit, required working directory, shown to the user
- environment is an explicit allowlist
- output streamed and bounded
- cancellation kills the child and its process group
- changed-file detection over the working directory produces a diff
- results are reviewed before anything is accepted

### 5.2 Prompt injection

File contents and AI responses are untrusted (`SECURITY.md` §7.3). An AI
response can never trigger a mutation, launch a process, or change settings,
providers or trust decisions.

### 5.3 Availability and degradation

A provider that is missing, unauthenticated, slow or failing produces a typed
error and a visible degraded state. It never produces an empty result
presented as complete.

---

## 6. Privacy

- local-first by default; remote providers are opt-in per provider
- before the first run of a provider, the user is told what leaves the machine
- a visible indicator shows when a remote provider is active
- AI job history is stored locally and can be cleared
- credentials live in the platform keychain (`SECURITY.md` §8)
